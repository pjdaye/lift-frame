This is the practitioner-facing companion to the taxonomy pages. The taxonomy tells you where AI-feature faults live — L-1 through L5B, the cross-cutting axes. This page tells you how to turn that into a test plan someone can execute and a release gate someone can enforce.

## Before You Start: Has This Feature Shipped?

Where you enter this Method depends on whether the feature already has production traffic.

**Not yet shipped, or no meaningful traffic yet:** start at Section 1. You can derive a complete test plan from an architecture description alone — every one of the four Worked Examples below was built this way, with no production data at all.

**Already shipped with real traces:** run an inductive error-discovery pass first, before Section 1. Read actual traces, build a lightweight review interface if you don't already have one, sample for diversity (cluster representatives plus random selections, not just the easiest cases to find), and let a human annotate freely without a preset category list — the goal is discovering failure modes, not confirming ones you already expect. Only then come back to Section 1: map what you found onto LIFT layers using the [Tagging Recipe](/lift-frame/lift/tagging-recipe/), and fold genuinely new failure classes into your risk register (Section 3) before finalizing eval packs (Section 5).

Skipping straight to Section 1 for a shipped feature risks missing idiosyncratic, product-specific failure modes that a general architecture taxonomy won't surface on its own — LIFT tells you where faults live structurally, not what your specific users are actually running into. The two are complementary, not competing: architecture-general taxonomy before launch or for net-new features, empirical discovery once real traces exist, feeding back into the same risk register either way.

*Further reading:* Hamel Husain and Shreya Shankar's [error-discovery skill](https://github.com/ai-evals-course/evals-skills/blob/main/skills/error-discovery/SKILL.md) is a concrete, ready-to-run methodology for this inductive pass, designed to be executed by a coding agent in an interactive session with a human reviewer.

Work through Sections 1–7 in order for a new feature. See **Worked Examples** below for four fully worked cases if you want to see a section in context before writing your own. These are distinct from the [Examples](/lift-frame/examples/) section elsewhere on the site: that section analyzes real, cited incidents retrospectively; the cases here are fictionalized prospective test plans built to teach this Method.

## Validation Status

The guidance below was synthesized from four independently converged, cross-model-scored test plans covering architecturally distinct features: a retrieval-based public chatbot, a tool-using assistant, a feature serving a vulnerable population through a pending model-capability change, and an agentic platform with irreversible tool access. Most of what follows is stated as direct guidance because it was arrived at independently and consistently across all four.

A smaller set of rules — noted where they appear — carry specific numeric thresholds (judge-agreement scores, sample sizes) that were consistent across all four cases but were generated by a single AI system in every case. Consistency across four different problem domains from one generator is real evidence that a mechanism transfers, but it is not yet independent confirmation that the specific numbers are optimal rather than a property of that generator. Those items are marked **provisional** below and are being re-validated against a second, independently developed test suite.

## 1. Determine Layer Applicability

Answer each question for your feature. "Yes," "No — structurally," or "Limited" all require one sentence of rationale; a blank or unjustified "N/A" is incomplete.

| Layer   | Applicability question                                                                                                                                                                                                              |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **L-1** | Does any vendor, third party, or upstream component (model, embeddings, fine-tune, retrieval index provider) sit outside your release control? This is nearly always yes for AI features — mark it N/A only with a specific reason. |
| **L0**  | Can user input, retrieved content, tool output, or session history plausibly be mistaken for an instruction?                                                                                                                        |
| **L1**  | Does the feature retrieve from a corpus, index, or knowledge base? If no, say so explicitly and name what would activate it later (adding RAG, adding search) so a future change re-triggers this section.                          |
| **L2**  | Does the system make a disposition decision (answer / clarify / abstain / escalate / plan) rather than returning a fixed lookup?                                                                                                    |
| **L2C** | Are there multiple agents, or any agent-to-agent handoff? If no, name the activation trigger (adding delegation), the same way as L1.                                                                                               |
| **L3**  | Does the feature call any tool, API, or execute any action with a side effect — including "read-only" tools, since schema and injection risk exist even without writes?                                                             |
| **L4**  | Is there any user-visible or externally-consequential output? Always yes.                                                                                                                                                           |
| **L5A** | Can the serving stack, model version, or configuration drift independently of your code changes? Always yes if L-1 is yes.                                                                                                          |
| **L5B** | Is the feature reachable by more than one session, user, or a public/anonymous surface?                                                                                                                                             |

**The manifestation rule**, applied identically across all four source cases: the primary layer is where a failure becomes visible or consequential; every other layer that enabled it is a contributing tag. A hallucinated fact that gets displayed is L4-primary even though L1 retrieval and L2 reasoning contributed. An unauthorized database write is L3-primary even though L0 injection enabled it. Apply this consistently — it's what makes cross-team tagging comparable.

*Further reading — L1:* [Classifying and Addressing the Diversity of Errors in RAG Systems](https://arxiv.org/abs/2510.13975), [GaRAGe](https://arxiv.org/abs/2506.07671), [PoisonedRAG](https://arxiv.org/abs/2402.07867).

## 2. Write the FRAME Contract

### 2.1 The candidate/final distinction

This is the load-bearing rule of the entire Method. Every converged plan, independently, built the same architecture: **model output is always a candidate**, inspected by a non-model component before it becomes final — displayed, executed, or committed. None of the four plans' invariants were satisfied by observing model behavior directly. A typed response schema rejected unrepresented claims; an output-policy classifier blocked prohibited categories before publication; a permission broker denied out-of-scope tool calls by default. All four stated, independently, that prompt compliance is not an enforcement mechanism.

Before writing a single invariant, name your candidate/final boundary. If you cannot name a non-model component that inspects candidate output before it has consequence, you do not yet have an invariant — you have a hope.

*Further reading:* [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/), [INJECAGENT](https://aclanthology.org/2024.findings-acl.624.pdf), [Prompt Injection Attack to Tool Selection](https://arxiv.org/abs/2504.19793).

### 2.2 Safety Invariants ("never")

Write each as: never-property → capability boundary or gateway that enforces it → deterministic oracle that verifies the boundary held. Every invariant must be automatable and release-blocking. A judge never decides an invariant in any of the four converged cases.

Common invariant families that recurred across all four (adapt, don't copy verbatim):

- Never take or claim an action beyond the feature's actual authorized capability
- Never let untrusted content — user text, retrieved passages, tool output, logs — change system policy, permissions, or instruction priority
- Never expose cross-session, cross-tenant, or otherwise isolated data
- Never release a changed upstream (L-1) component without re-certification (the Tessa Rule — Section 2.5)
- Never report a status, completion, or recovery claim without a matching authoritative receipt (the truthfulness pattern below)

**The truthfulness pattern.** All four plans arrived separately at the same solution for "the system must not lie about what happened": render status claims only from structured, signed receipts, never from generated prose. The strongest instance distinguishes agent-authored from verified/restored provenance explicitly, so a system cannot present fabricated-but-plausible output as if it were verified fact. If your feature makes any claim about system state, action success, or data provenance, build this distinction in from the start rather than retrofitting it later.

### 2.3 Quality Envelopes

Name a specific confidence-interval method per metric — Wilson, Clopper-Pearson, bootstrap, or a nonparametric tolerance bound for continuous metrics like latency — never a bare threshold. State the sampling plan, required slices, and the decision rule for what happens if a slice lacks sufficient n.

A non-negotiable principle stated independently in all four plans: **no aggregate result may mask a failing slice.** Every plan required per-slice pass/fail — by population, especially vulnerable slices, by adversarial/benign intent, by language, by architectural variant — with an explicit "insufficient evidence" outcome, not a pass, when a slice's sample size is too small.

**Provisional refinement:** the strongest of the four cases treats listed sample sizes as minima recomputed before every test campaign, so the worst-case confidence-interval half-width never exceeds the tolerance band, rather than a fixed number chosen once at design time. Recommended as the default over a fixed-n approach.

### 2.4 Liveness Objectives ("eventually")

Every liveness property needs one of two verification techniques, not just a stated time bound:

- **Virtual-clock or fault-injection tests** for anything simulatable deterministically — timeouts, retries, escalation timers, kill-switch propagation.
- **Scheduled drills** for anything that can't be safely simulated in CI — real paging systems, real rollback or restore.

Do not accept "the monitoring infrastructure that would detect this exists" as evidence that a liveness bound is met. The infrastructure existing and the SLA being verified are two different claims — this exact gap was the single blocking issue in the one converged case that needed a third iteration, and it was specifically the case with a retrieval-based architecture. Retrieval-heavy features should budget for an additional validation round on this basis.

*Further reading:* [Defining Liveness (Alpern & Schneider)](https://www.cs.cornell.edu/fbs/publications/DefLiveness.pdf) is the formal basis for the never/eventually split this Method borrows throughout, and for why the two categories need different verification strategies rather than one.

### 2.5 Evidence Obligations and the Tessa Rule

**The Tessa Rule**, implemented identically across all four cases: any change to a vendor model, upstream component, fine-tune, or third-party dependency triggers the full applicable eval-pack suite before production exposure. A capability-class change — rule-based to generative, single-tool to multi-tool — additionally reopens the FRAME contract itself for review. The rule isn't "re-run the tests," it's "re-examine whether your invariants still apply."

Every case, test, and incident should retain enough to reconstruct the decision without live production access: configuration and model hashes, the exact input and retrieved or tool context, the deterministic oracle's inputs and result, and the release disposition. All four cases required a specific replay test reconstructing a decision from stored evidence alone, with any mismatch blocking release.

*Further reading:* [NIST AI RMF 1.0](https://nvlpubs.nist.gov/nistpubs/ai/nist.ai.100-1.pdf) for the governance framing behind change management; [MITRE ATLAS](https://atlas.mitre.org/) for supply-chain and poisoning threat patterns relevant to L-1.

## 3. Build the Risk Register

Score every identified risk as Severity × Likelihood × Detectability → Tier. This formula was independently spot-checked and found error-free across every risk row in every one of the four cases — apply it consistently rather than revising it.

**The vulnerable-population floor.** Where a harm could affect a vulnerable population — minors, people in crisis, medically or psychologically vulnerable users — severity floors at S1 regardless of aggregate likelihood, and an aggregate pass cannot offset a failure in the vulnerable-population slice. All four cases implemented this as a hard, separately-reported statistical requirement.

**Extend "affected population" beyond direct users.** The strongest of the four cases applies the vulnerable-population floor to people affected by the system who never interact with it directly — the operator's customers, whose data the system can touch. If your feature's actions can affect people who aren't the ones using it, include them in your population analysis.

Tier drives evidence requirement, not effort level: T1 gets an automated gating oracle plus a statistical envelope at 95% confidence or higher; T2 gets a per-release test plus a production reason code; T3 gets sampled or exploratory coverage, or a named, expiring waiver. No T1 risk should ever have a coverage-matrix cell with zero tests.

## 4. Build the Coverage Matrix

Cross layers (L-1 through L5B) against the cross-cutting attack-pattern axis (extraction, injection, escalation, resource abuse, trust manipulation, supply-chain poisoning) and state scope (stateless, session, cross-session, system). Mark each applicable cell's tier and the test IDs that cover it; mark structurally inapplicable cells with a one-line architectural reason, not a blank.

Exit criteria, convergent across all four: every T1 cell is an automated, passing, evidence-producing gate — no manual waivers on T1 by the product team alone. T2 cells need a per-release test and live monitoring. T3 needs either a sampled/exploratory charter or a named, expiring waiver, never silence.

## 5. Select and Adapt Eval Packs

The eleven packs — gold-answerable, unanswerable/abstain, ambiguity/clarify, conflict handling, user prompt injection, content/corpus injection, rights/embargo, staleness, harm-domain probes, capability boundary, and economic abuse — are domain-agnostic in structure; their content is entirely feature-specific and should be. What's convergent across all four cases is the construction discipline, not the content:

- Split cases into a frozen regression set, a blinded holdout never used to tune the system, and a periodically refreshed set drawn from real, redacted, consented field data
- Every pack includes both benign and adversarial intent where meaningful
- Every case is tagged with its provenance, generation method, and deduplication status, and audited for training/eval contamination
- The capability-boundary pack specifically requires comparing prompt-level refusal against actual mechanical denial — only mechanical denial counts as passing. This is what separates a real capability boundary from a well-behaved model that happens to refuse.

Where a layer is architecturally inapplicable — no retrieval, so the corpus-injection pack has nothing to inject into — adapt the pack to the nearest real analog (tool-result content, for example) rather than marking the whole pack not applicable.

## 6. Design Compositional Scenarios

The four converged cases used entirely different chains, because their architectures were different — that's correct. What's convergent is the method for building a chain, not any specific chain:

1. Identify a plausible multi-layer path: something that starts as a contributing-layer event (an input-boundary injection, an upstream vendor change, a context-truncation event) and traces forward to where it would actually manifest.
2. Assert per-hop, not just at the end. Each step gets its own pass/fail check, so a failure localizes to a specific hop.
3. Where a hop represents a privilege or consequence boundary, stop the scenario there on failure — don't let a test proceed to a later hop after an earlier gate should have blocked it.
4. Aim for at least three chained scenarios covering distinct combinations of layers; all four converged cases exceeded this minimum.

*Further reading:* Microsoft's [Taxonomy of Failure Modes in Agentic AI Systems](https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/final/en-us/microsoft-brand/documents/Taxonomy-of-Failure-Mode-in-Agentic-AI-Systems-Whitepaper.pdf) maps well onto multi-agent and tool-chaining scenarios specifically.

## 7. Wire Operational Integration

### 7.1 Reason Codes and Dashboards

Every case distinguished attempted-and-blocked events from escaped-and-published events in its reason-code taxonomy, and every case warned against letting a dashboard conflate them — a high rate of blocked attempts is a control working, not an incident rate rising. Design your taxonomy with this split from day one; retrofitting it later means historical data can't be re-interpreted cleanly.

### 7.2 Drift Monitoring

Use control charts — p-charts for proportions, individuals or X-bar/R charts for continuous metrics like latency and cost — with pre-registered out-of-control rules (a common convergent set: one point beyond three standard deviations, two of three beyond two, eight consecutive points on one side of center). Baselines come from the certified release configuration and are only re-established through change control, never silently reset after an alert.

### 7.3 Change Re-certification

Tier your re-test scope by what changed:

- **Capability-class or upstream change:** full applicable eval-pack suite, plus a FRAME-contract review if the capability class itself changed
- **Prompt, policy, or configuration change:** affected T1 cells plus fixed regression and compositional suites
- **Judge change (model, prompt, or rubric):** full re-qualification
- **Production incident:** immediate regression-case addition, before the next release if the incident was severe

### 7.4 Judge Qualification (only if a judge is used at all)

**Provisional:** if any LLM judge participates in scoring, all four cases converged on the same structure and the same numeric thresholds — a golden set of at least 100 human-adjudicated items, agreement of at least 0.80 overall and 0.75 on any critical or vulnerable-population slice, a judge model family different from the system under test, documented and quantified bias probes, and mandatory requalification quarterly or on any judge/prompt/rubric change, with automatic exclusion rather than a grace period if qualification lapses. The strongest of the four cases went further and excluded judges from safety gates entirely, restricting them to non-gating quality scoring. Treat the categorical exclusion as the safer default; treat the exact numeric thresholds as strong defaults pending independent confirmation.

**Report TPR/TNR alongside agreement, not instead of it.** A single aggregate agreement score can hide which of two very different failure modes a judge has: missing real failures (low true-positive rate) versus over-flagging good output (low true-negative rate). For any judge backstopping a T1-adjacent quality dimension, set an explicit TPR floor on the failure class specifically, not just an overall agreement number — a judge that agrees with humans 85% of the time but is weak specifically at catching the failure you care about is a worse risk than the aggregate number suggests.

*Further reading:* [LLMs-as-Judges Survey](https://arxiv.org/abs/2412.05579); on the specific biases the qualification protocol probes for — [position bias](https://aclanthology.org/2025.ijcnlp-long.18.pdf) and [self-preference bias](https://arxiv.org/abs/2410.21819); on the TPR/TNR calibration methodology specifically — Hamel Husain and Shreya Shankar's [validate-evaluator skill](https://github.com/ai-evals-course/evals-skills).

### 7.5 Field-Report Intake

Every case built a path for external reports to become severity-classed regression cases: an intake channel with an acknowledgment SLA tied to severity, automatic evidence preservation, and a requirement that confirmed and credible near-miss reports become regression cases before the next release for anything high-severity. This closes the loop that fails when a known risk surfaces externally and goes unactioned before it recurs in production.
